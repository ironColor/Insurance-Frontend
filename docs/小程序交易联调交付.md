# 小程序交易联调交付

## 依据与实现

依据根目录 Word 后端回复及 GET https://www.zfxbaoxian.com/prod-api/wxmini/v3/api-docs 全文解析。Swagger validBeforePay 旧 summary 与 Word 冲突，按 Word：code=200 且 msg 空直接预支付；非空需确认；非 200 阻断。

- 新单不传 orderNo；续付带 orderNo、服务端 payAmount。金额支持元字符串，新单整数分累加。
- orderData 使用 productId/productName/选中 planGroupList/blockConfigList；字段使用保留的英文 fieldName，不猜中文映射。
- 退款仅 PAID，必选 pay_refund_reason 字典，金额取 payAmount，remark 与整数 refundChannel=1 按 schema。
- 订单状态采用 NOTPAY/PAID/CANCELLED/CLOSED/REFUNDING/REFUNDED；支付 SUCCESS；退款 SUCCESS 显示成功，其余未知码保留原文，不沿用 Swagger 过时数字枚举。
- 隐藏主动取消；不把 policyStatus 当承保成功。
- 新单发送前持久化 account/product pending；返回 orderNo 即记录 known（包括卸载后响应），刷新可恢复续付。无 orderNo 的未知请求不自动新建重试。
- 已知记录允许用户明确选择“另填一份投保”，不会永久锁住该产品。未知记录不能自行清除。
- 旧 pay pending 因已有 orderNo 可复用支付单而不阻断续付；旧 refund pending 在 PAID 且无退款记录时保守阻断。新版退款发送中不会清除锁；请求结束后手动刷新按后端回复恢复，查询状态由后端决定资格。

## 残留风险（上线前必须知悉）

1. 后端明确目前不重算方案金额，前端校验不能抵御篡改客户端；服务端重算和校验金额是必须的安全加固。
2. 无新单幂等键/找回接口。响应丢失且未拿到 orderNo 时，需用户查询订单或人工核实；清缓存/换设备无法保证去重。
3. 多选格式 Word 未明确，沿用现有“、”分隔格式并映射 option value，需后端确认与联调。
4. 退款超时后刷新再试按 Word 实现；服务端需保证退款重复提交校验和读写一致性。旧未知退款不会因一次 PAID/无记录误开放。
5. 字典读取失败时状态退回已知标签/原码；退款原因无字典不允许猜值提交。
6. 实际微信支付参数和退款到账回调仍需在授权测试环境验收。
