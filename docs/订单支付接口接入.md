# 小程序订单支付接口接入与契约缺口

依据：完整读取 `https://www.zfxbaoxian.com/prod-api/wxmini/v3/api-docs` OpenAPI 3.1 paths 与 components.schemas（本次实现），不沿用旧文档“没有支付接口”的结论。

## 已实现

> 服务层已接入，但支付、取消、退款页面入口目前均受状态契约阻断，不能发起资金写请求。以下调用链保留用于本地 mock 测试及后续补齐契约，不代表已开放交易。UI 统一提示：“订单状态规则待服务方确认，暂不能执行该操作”。

- `/order/list`：分页 rows/total（不是 data），按订单号查询、刷新、加载更多、错误重试；不再读取本地模拟订单。
- `/order/{orderId}` 与 `/order/getOrderByOrderNo/{orderNo}`：真实详情，核验订单身份；金额、支付时间、保单号/期间/状态来自服务端。
- `/pay/channelList/{productId}`：裸数组，选择启用渠道 id；method 固定文档定义的小程序 `4`。
- `/pay/validBeforePay` → `/pay/prepay`：现有服务端订单再次查询后，复用服务端金额及不透明 orderData；业务警告需用户确认。HTTP 异常、401/403、业务 5xx、响应缺 code 不允许继续。
- `PayResponseDTO.packageStr` 映射微信 requestPayment.package，校验签名和订单号；不读取或执行 payForm/callback。客户端取消、未知与已提交均进入服务端查询，不写本地成功状态。
- `/pay/cancelOrder/{orderNo}`：按文档 GET，但它是写操作，仅明确点击确认后调用。取消后刷新，失败提示结果待确认。
- `/pay/applyRefund`：只提交 orderNo、remark、refundChannel=1，不猜退款原因字典、不传自行计算的退款金额。受理不等于到账，退款记录从订单 refundList 查询。
- 退款记录仅映射文档明确的 0申请中/1退款中/2成功/3失败/4拒绝，未知值显示待确认。
- 登录使用 xcxCode/clientId/appid；手机号绑定使用 phoneCode；资料 PUT/user 与上传 file 字段和当前文档匹配，保持原有实现。首页和产品 allInfo/decodeScene 已有真实接入，不重复调用基础 product 接口。

## 不可猜测的边界（上线前需后端确认）

1. **新单仍阻断**：PayRequestDTO.orderData 只有 string，无 JSON schema/示例。表单配置 fieldId 与 fieldName、方案组选中项、选项值和投保人列表如何组织，没有定义。不得把本地 InsuranceDraft 序列化冒充正式投保请求。新单付款页面显式说明原因；没有创建假订单。
2. `pay_status`、`pay_order_status`、`pay_policy_status` 未列枚举，无字典查询接口，也没有明确的操作能力响应契约。页面仅显示原始代码，支付/取消/退款全部显式阻断；不猜数字、不以 payTime 或其他人类可读时间戳推断已付或可操作，也不信任自行发明的 capabilities 字段。需服务方明确各操作允许的状态组合或正式能力响应后，才可实现并测试门禁放行规则；validBeforePay 的业务警告确认不能绕过此门禁。
3. `pay_refund_reason` 无枚举/查询接口。申请说明放入可选 remark，不提交中文标签或任意数字到 refundReason。
4. 渠道没有小程序能力标识，页面显示启用渠道供选择，提交 method=4，由服务端校验；若需只显示微信渠道，后端须提供明确 code 枚举或能力字段。
5. 无独立退款查询、取消退款、保单下载、理赔、投诉、学校查询接口；不虚构。
6. 支付、取消、退款写请求一旦发出可能已到达服务端，即使超时、客户端取消支付、响应异常或离开页面，也不能视作未执行。调用链在发送前同步持久化 `insurance-order-pending:v1:<登录userId>:<orderNo>:<action>`；重进页面、模块重载与小程序重启仍阻止同用户同订单同操作重发。缺 userId 或本地存储失败时阻断。退出登录不删除 pending，不存 token 或支付签名。当前采用保守记录：支付在 validBeforePay 前记录，因此用户取消警告也不自动清除。查询返回未知状态、成功回调或时间戳均不自动解除。恢复依赖服务方补齐幂等键、写结果查询及可安全重试/终态契约，再实现明确的核对恢复流程；不能要求用户清缓存来重试。清除本地数据、换设备或多端操作仍需后端幂等兜底，不能宣称客户端提供全局恰好一次。
7. `amount` 必填但计价/优惠及应付金额语义不完整；已有订单采用服务端 totalAmount，而非本地保费。有非零 discountAmount 的订单阻断付款，优惠订单最终应付字段需后端明确。

## 验证与安全

`npm run test:order` 使用 VM 注入 Taro 网络与支付 API，仅本地响应，没有真实网络。覆盖数组/分页 envelope、大整数ID、鉴权失效、业务警告、服务异常、取消、未知结果和退款字段，以及生命周期代次失效、校验/确认期间卸载中止、资金门禁、pending 持久化与账号隔离、存储失败阻断。typecheck/build 另行执行。

支付页查询、校验、确认、预支付、原生支付回调后的状态更新和导航均检查生命周期代次；退款与取消同样检查每次 await 后是否仍有效。已发出的请求无法撤回，pending 不因卸载清除。onHide 不视为卸载，避免原生支付面板隐藏页面时中断正常返回。列表输入词与提交词分离，只有点击查询更新提交词，后续分页/刷新/重试沿用提交词。

本次未发送任何生产登录、绑定手机号、下单、支付、取消或退款请求。真实设备微信支付、商户配置、合法域名和测试环境端到端联调仍需交付前验收。不得在生产用真实订单探测契约。
