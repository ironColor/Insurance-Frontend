# 后续开发指南

> 本文帮助开发者和 AI 从当前工作区开始定位、实现及验收功能。以下步骤是开发建议，未代替业务确认，也未表示本次已执行构建、接口联调或支付测试。

## 一、开始开发时先了解什么

建议按以下顺序阅读：

1. [项目说明](../项目说明.md)：先掌握两个目录的职责、当前完成程度、业务流程与差异编号。
2. 当前仓库的 [AGENT.md](../AGENT.md)：确认本端技术栈、脚本、依赖和编码配置。
3. [原型与功能索引](./原型与功能索引.md)：找到当前功能对应画布、页面状态、批注日期及版本。
4. [接口与数据模型](./接口与数据模型.md)：确认已存在的请求、服务字段、编码和跨端适配缺口。
5. 对应页面、服务与类型源码：以正在开发的工作区为准，重新核对相关行为。

项目有几个容易误判的地方：

- `Insurance-Frontend` 是小程序，`Insurance-mana-front` 是 PC；两者是独立仓库。
- PC 产品、横幅、合作公司已编写服务请求；PC 订单仍使用内存示例。
- 小程序产品和投保模型是本地配置；订单读取本地存储；支付及退款提交尚未接入。
- 同名 `ProductConfig` 并不代表共享类型；PC 的接口模型与小程序的本地模型不同。
- 当前原型包含弃用稿、二期稿、备用稿与相同页面的不同状态；不能按目录数量创建新路由。
- 框架目录中存在工作流、租户或示例代码，不代表这些模块已经列入保险项目本期范围。

跨端需求应同时检查两端映射，例如“后台改变阅读规则”必须检查小程序是否能读取并执行，而不只检查 PC 保存成功。

## 二、本地启动与配置入口

### 2.1 小程序

仓库 README 声明 Node.js 18 及以上、npm 9 及以上；根目录存在 `package-lock.json`。当前工作区已有依赖目录，新环境应根据实际 Node 兼容性和锁文件准备依赖。

```sh
cd /Users/macbook/Desktop/Insurance/Insurance-Frontend
npm ci
npm run dev:weapp
```

使用微信开发者工具导入小程序项目，结合根目录 `project.config.json` 和构建输出 `dist/` 调试。小程序 AppID、开发者权限和请求合法域名需要由项目维护者提供或在已有配置中确认。浏览器预览不能替代微信环境中的手机号授权、扫码及原生支付验收。

| 配置位置 | 作用 |
| --- | --- |
| `config/index.ts` | Taro/Vite、设计宽度750、源码及输出目录、构建行为 |
| `config/dev.ts`、`config/prod.ts` | 环境构建扩展，目前配置较少 |
| `project.config.json` | 微信开发者工具项目设置 |
| `src/app.config.ts` | 16个页面及全局窗口配置 |
| `src/services/api.ts` | 当前固定业务地址、请求和上传封装 |
| `src/services/auth.ts` | 微信授权及手机号绑定服务 |

当前小程序业务地址在源码中固定，没有完整的环境切换方案；接测试环境时应先明确配置入口，避免误连生产接口。

小程序静态检查和构建命令：

```sh
npm run typecheck
npm run build:weapp
```

### 2.2 PC 后台

根 `package.json` 声明 Node.js 20.19.0 及以上、npm 8.19.0 及以上。README 使用 npm，仓库同时存在 `yarn.lock`，未声明统一 `packageManager`；新环境安装前应确认团队锁文件策略，避免无关依赖升级。

已准备依赖后启动：

```sh
cd /Users/macbook/Desktop/Insurance-mana-front
npm run dev
```

| 配置位置 | 作用 |
| --- | --- |
| `vite.config.ts` | 基础路径、服务端口、代理、插件 |
| 环境变量 `VITE_APP_BASE_API` | Axios基础前缀与开发代理匹配 |
| 环境变量 `VITE_APP_CONTEXT_PATH` | 应用基础路径 |
| `src/settings.ts` | 主题、侧栏、头部、页签等框架设置 |
| `src/router/index.ts` | 固定页面路由 |
| `src/permission.ts`、权限store | 登录守卫、服务端菜单和动态路由 |
| `src/utils/request.ts` | 鉴权、错误、重复提交、可选加密和上传处理 |

端口和环境值依运行配置确定，本文不记录账号密码、令牌、加密材料或环境文件内容。实际开发需要有相应角色账号，并确认服务端返回了保险菜单和字典。

PC 构建及现有产品测试入口：

```sh
npm run build:dev
./node_modules/.bin/vue-tsc --noEmit
./node_modules/.bin/vitest run
```

当前没有单独的 `test` 脚本，Vitest 配置只包含 `src/**/__tests__/*.test.ts`，采用 Node 环境。上述命令用于后续开发验证，本次文档整理没有执行，也不承诺现有代码全部通过。ESLint 可针对改动文件执行；不要为单个功能运行全仓库格式化而产生大量无关差异。

## 五、分阶段接入建议

| 阶段 | 需要的前置契约 | 交付目标 | 对应差异 |
| --- | --- | --- | --- |
| 1 产品驱动展示 | 小程序产品详情、字典、媒体、文档、有效性与版本 | 一个后台配置可完整驱动介绍、方案、投保字段及阅读 | 01、05、06、12、17 |
| 2 入口和身份 | 扫码参数、登录恢复、地区/学校归属、历史被保人权限 | 直接扫码和首页进入都保留正确产品上下文 | 02、03、04、18 |
| 3 订单服务 | 服务端校验、去重范围、报价、幂等、快照、分页与数据范围 | 真正创建/恢复订单，替换两端示例数据 | 07、08、19 |
| 4 微信支付 | 预支付参数、回调、查询、订单时限、允许支付状态 | 成功、取消、失败和未知结果形成可靠闭环 | 08、09 |
| 5 退保退款 | 资格、试算、原因、提交、审批/退款状态及原路返回 | 服务端金额和进度驱动退款页面 | 10 |
| 6 运营补齐 | 真实统计/导出、链接承载、组织权限、资料及校验边界 | 可按产品查看真实业务数据，并对齐剩余设计 | 11、13、14、15、16、20、21 |

“差异”编号对应项目说明第八部分，只用于跟踪。每阶段先确认相关未决规则，再形成页面范围、接口契约和验收条件；若当前任务只是小范围修复，可按其依赖完成，无需一次重写整个项目。

## 六、关键验收场景

以下是未来实现的验收建议，不表示当前代码已满足。应使用获授权的测试环境和测试资料。

| 模块 | 应覆盖的场景 |
| --- | --- |
| 登录与入口 | 正常授权、取消手机号、手机号绑定失败、会话过期；扫码前未登录，登录后恢复同一产品；无效/禁用/过期参数提示 |
| 首页 | 无横幅/无公司、图片加载失败、禁用数据过滤、排序；同时配置产品和链接时优先产品，只有链接时按确认方式打开 |
| 产品读取 | 缺失配置、下线产品、旧草稿版本、长ID、远程媒体失败；读取异常不能继续用另一个产品的旧内容投保 |
| 方案选择 | 必选分组未选阻止继续；附加险取消；超过两个标签；切换方案联动责任和详情；显示金额两位小数与服务端报价一致 |
| 投保字段 | 所有确认支持的字段类型、必填、身份证/手机号、选项、多选、格式及业务规则；错误位置和提示；学校不在有效范围 |
| 阅读与协议 | 未勾选协议禁用；点协议链接不自动勾选；返回按确认规则重置；多份依序阅读；滚动、时长及组合；记录文档版本和完成情况 |
| 重复投保 | 服务端发现已支付记录；用户取消/确认；查询失败；并发提交；去重范围边界；确认后重新校验许可 |
| 创建订单 | 重复点击、弱网重试、创建成功但响应丢失、草稿恢复、金额变化、配置变化；不产生重复订单 |
| 支付 | 正常成功、用户取消、渠道失败、回调延迟、前端结果未知、返回后恢复、超时关闭；以服务端查询为准 |
| 订单 | 本人/权限范围、状态筛选、关键词、分页、详情快照；失效/已支付/退款订单不可重复支付；历史方案不随配置更新漂移 |
| 退款 | 不符合资格、试算失败、未选原因、未勾风险、200字边界、重复提交；处理中/失败/完成；金额及到账信息来自服务端 |
| 产品保存 | 新建返回ID、分区保存、整份临时保存、回读失败、复制清理主键、未知字段保留、已有订单锁定、禁用状态 |
| 上传及文件 | 类型/大小边界、上传失败、缺失URL、非法临时URL、重复选择、富文本/链接/附件三种文档 |
| 统计与导出 | 当前产品范围、状态和日期筛选；保费扣退款/订单扣退单；分页不影响全部匹配导出；导出权限与脱敏 |
| 布局 | 微信真机状态栏/胶囊/安全区、长表单、键盘、浮层滚动、固定底栏；PC长文本、宽表格和详情抽屉 |

有服务端状态或持久化影响的功能，应结合请求和服务返回核对，不能仅凭提示“成功”或按钮变化判定完成。金融结果必须使用服务端订单/退款状态，不使用本地 `status` 作为支付凭证。

## 七、文档与变更维护

- 本次 PC 工作区原本已有未提交业务及测试改动，后续任务先检查 `git status`，保留这些改动并辨别当前任务范围。
- 调整页面或业务规则后，同步两个目录的 `项目说明.md` 和 `docs` 三份文档；两端 `AGENT.md` 只更新各自事实。
- 新接口补充路径、方法、输入/输出、状态、错误和权限约定；未确认字段标记待确认，不自行编造后端行为。
- 原型修订时记录画布、页面、批注日期与版本，保留“代码现状”和“设计要求”的区别。
- 更新对应差异编号的状态，并记录实际执行的检查及结果；不把构建通过写成接口或支付验收通过。
- 当前文档中的绝对路径用于本机定位，迁移项目后应调整链接；业务模型与原型入口不依赖这些本机路径。

完成任务时应说明具体变化、受影响页面、验证方法和剩余未决项，使下一次 AI 开发能够继续当前上下文。
